# Tầng Application
Chịu trách nhiệm cung cấp giao diện lập trình (API) và quy chuẩn giao tiếp cho các tiến trình ứng dụng (Application Processes) trao đổi dữ liệu qua mạng thông qua khái niệm Socket (IP:Port)
## 1. HTTP/HTTPS (Hypertext Transfer Protocol / Secure)
### Khái niệm
Là giao thức truyền tải dữ liệu siêu văn bản hoạt động theo mô hình Client-Server ở dạng văn bản thô(Plaintext). HTTPS là phiên bản có tích hợp thêm bảo mật của HTTP, tích hợp thêm lớp mã hóa TLS/SSL ở Layer6 để bảo vệ dữ liệu truyền tải dữ liệu qua mạng.

### Dùng để làm gì
- Được dùng để truyền tải các tài nguyên tran web(HTML, CSS, JS, hình ảnh, video)
- Làm nền tảng truyền tải cho các ứng dụng web, RESTFullAPI, gRPC-Web và microservices

### Cấu trúc thành phần
Gói tin HTTP dựa trên dạng văn bản (Text-based), gồm 3 phần chính:
```
[ Request / Status Line ]
[ Headers (Key: Value)  ]
[ CRLF (\r\n)           ]
[ Message Body (Payload)]
```
- Request Line (Client $\rightarrow$ Server): [Method] [Request-URI] [HTTP-Version] (Ví dụ: `GET /index.html HTTP/1.1`).
- Status Line (Server $\rightarrow$ Client): [HTTP-Version] [Status-Code] [Reason-Phrase] (Ví dụ: `HTTP/1.1 200 OK`).
- Headers: Chứa metadata như Host, User-Agent, Content-Type, Authorization, Cookie, Cache-Control.
- Body: Chứa dữ liệu thực tế (JSON, HTML, Binary File...)

### Các file hệ thống trong Linux
Nginx Web Server:

- File cấu hình chính: `/etc/nginx/nginx.conf`
- VirtualHost configs: `/etc/nginx/sites-available/`, `/etc/nginx/sites-enabled/` hoặc `/etc/nginx/conf.d/*.conf`
- Log files: `/var/log/nginx/access.log`, `/var/log/nginx/error.log`

Apache Web Server:

- File cấu hình chính: `/etc/httpd/conf/httpd.conf` (RHEL/CentOS) hoặc `/etc/apache2/apache2.conf` (Ubuntu/Debian)
- Log files: `/var/log/httpd/` hoặc `/var/log/apache2/`
- Thư mục Web Root mặc định: `/var/www/html/`
- Chứng chỉ SSL/TLS: `/etc/ssl/certs/`, `/etc/pki/tls/`, `/etc/letsencrypt/live/`

### Cấu hình như thế nào
Thực hiện cấu hình bằng cách viết file. Ví dụ mẫu 1 file cấu hình của nginx:
```
server {
    listen 80;
    server_name app.example.com;
    return 301 https://$host$request_uri; # Redirect HTTP sang HTTPS
}

server {
    listen 443 ssl http2;
    server_name app.example.com;

    ssl_certificate /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```
### Cơ chế hoạt động
Khởi tạo: Client thiết lập kết nối TCP 3-Way Handshake tới Port 80 (HTTP) hoặc Port 443 (HTTPS)

TLS Handshake (HTTPS): Thỏa thuận thuật toán mã hóa, xác thực Digital Certificate và tạo Session Key

Request: Client gửi gói tin HTTP Request qua socket

Processing: Web Server/Reverse Proxy tiếp nhận, xử lý hoặc chuyển tiếp tới Backend

Response: Server trả về HTTP Response + Status Code

Closing / Persistence: Đóng kết nối hoặc giữ kết nối mở (Keep-Alive)

### Ưu/Nhược điểm
Ưu điểm: Linh hoạt, mở rộng tốt, hỗ trợ Caching mạnh mẽ, là chuẩn chung toàn cầu.

Nhược điểm: 
- HTTP thô không mã hóa; 
- `HTTP/1.1` bị nghẽn Head-of-Line Blocking; 
- Stateless nên cần Session/Cookie/Token để duy trì ngữ cảnh.

## 2. DNS (Domain Name Systems)
### Khái niệm
DNS là hệ thống cơ sở dữ liệu phân tán theo tầng, đóng vai trò như "danh bạ Internet" để phân giải tên miền thành địa chỉ IP và ngược lại.

### Dùng để làm gì?
Phân giải tên miền (`google.com` $\rightarrow$ `142.250.198.46`).

Định hướng máy chủ Mail (MX Record), định cấu hình bảo mật tên miền (TXT: SPF, DKIM, DMARC), định vị dịch vụ (SRV Record).

### Cấu trúc thành phần
Gói tin DNS chạy trên Port 53 UDP/TCP, có cấu trúc khung cố định 12-byte Header:
```
+---------------------+---------------------+
|        ID (16 bits) |     Flags (16 bits) |
+---------------------+---------------------+
| QDCOUNT (Question)  | ANCOUNT (Answer)    |
+---------------------+---------------------+
| NSCOUNT (Authority) | ARCOUNT (Additional)|
+---------------------+---------------------+
| Questions / Resource Records (RR) Payload |
+-------------------------------------------+
```
Header: Chứa ID truy vấn, các Cờ (Flags: QR, Opcode, AA, TC, RD, RA, RCODE) và số lượng bản ghi.

Question Section: Tên miền cần tra cứu (QNAME), Loại bản ghi (QTYPE: A, AAAA, MX...), Lớp (QCLASS: IN).

Answer / Authority / Additional Sections: Chứa các bản ghi Resource Record (RR) bao gồm TTL, RDLENGTH và RDATA (địa chỉ IP hoặc tên miền mục tiêu).

### Các file trong hệ thống Linux
Client Resolver Config: `/etc/resolv.conf` (Chỉ định IP DNS Server dùng để tra cứu).

Name Service Switch: `/etc/nsswitch.conf` (Quy định thứ tự ưu tiên tra cứu: hosts: files dns).

Static Host Mapping: `/etc/hosts` (Bảng ánh xạ IP-Domain thủ công nội bộ).

Systemd Resolver Service: `/etc/systemd/resolved.conf`

BIND9 DNS Server:

- File cấu hình chính: `/etc/bind/named.conf`, `/etc/bind/named.conf.options`

- Zone files (chứa bản ghi): `/etc/bind/zones/db.example.com`

- Log files: `/var/log/named/` hoặc `journalctl -u named`

### Cấu hình như thế nào?
File `/etc/resolv.conf` (Client):
```
nameserver 1.1.1.1
nameserver 8.8.8.8
search localdomain
```
File Zone BIND9 `/etc/bind/zones/db.example.com`:
```
$TTL    86400
@       IN      SOA     ns1.example.com. admin.example.com. (
                        2026033001 ; Serial
                        3600       ; Refresh
                        1800       ; Retry
                        604800     ; Expire
                        86400 )    ; Minimum TTL
;
@       IN      NS      ns1.example.com.
ns1     IN      A       192.168.1.10
web     IN      A       192.168.1.50
```
### Cơ chế hoạt động
Quy trình Recursive Lookup (Truy vấn đệ quy) khi gõ `web.example.com`:
```
[Client] ──(1. Ask)──> [Local Resolver] ──(2. Ask)──> [Root Name Server (.)]
                            │                 <──(3. Refer)──
                            ├──(4. Ask)──> [TLD Server (.com)]
                            │                 <──(5. Refer)──
                            └──(6. Ask)──> [Authoritative Server (example.com)]
                                              <──(7. IP Data)──
```
- Client kiểm tra Cache cá nhân $\rightarrow$ Kiểm tra file `/etc/hosts` $\rightarrow$ Gửi request lên Local Resolver (IP cấu hình trong resolv.conf).
- Local Resolver gửi câu hỏi lên Root Name Server (.).
- Root Server trả về IP của TLD Server (.com).
- Local Resolver tiếp tục hỏi TLD Server (.com).
- TLD Server trả về IP của Authoritative DNS Server quản lý miền example.com.
- Local Resolver hỏi Authoritative Server và nhận IP chính xác của `web.example.com`.
- Local Resolver lưu vào Cache và trả kết quả cuối cùng cho Client.

### Ưu / Nhược điểm
Ưu điểm: Phân giải địa chỉ linh hoạt, có khả năng phân tải (DNS Load Balancing via Round-Robin), cơ chế Caching giúp phản hồi cực nhanh.

Nhược điểm: Bản chất UDP thô dễ bị tấn công DNS Spoofing / Cache Poisoning (cần triển khai DNSSEC) và DNS Amplification Attacks.

## 3. DHCP (Dynamic Host Configuration Protocol)
### Khái niệm
DHCP là giao thức cấu hình host động, tự động phân phát địa chỉ IP và các thông số mạng liên quan cho thiết bị khi truy cập vào mạng.

### Dùng để làm gì?
Tự động gán IP Address, Subnet Mask, Default Gateway, DNS Server, NTP Server cho các máy trạm.

Tránh xung đột IP (IP Conflict) và tối ưu hóa việc quản lý địa chỉ IP tĩnh/động trong LAN.

### Cấu trúc thành phần
Chạy trên Port 67 UDP (Server) và Port 68 UDP (Client). Khung dữ liệu DHCP Message có cấu trúc:
```
[ OP (1 Byte) | HTYPE (1) | HLEN (1) | HOPS (1) ]
[ XID - Transaction ID (4 Bytes)                ]
[ SECS (2 Bytes)              | FLAGS (2 Bytes) ]
[ CIADDR - Client IP Address (4 Bytes)          ]
[ YIADDR - Your IP Address (4 Bytes)            ]
[ SIADDR - Server IP Address (4 Bytes)          ]
[ GIADDR - Gateway IP Address (4 Bytes)         ]
[ CHADDR - Client Hardware MAC (16 Bytes)       ]
[ OPTIONS (Biến đổi - Magic Cookie: 0x63825363) ]
```
Các DHCP Options quan trọng:
- `Option 53`: DHCP Message Type (Discover, Offer, Request, ACK...).
- `Option 1`: Subnet Mask.
- `Option 3`: Router / Default Gateway.
- `Option 6`: DNS Server.
- `Option 51`: IP Address Lease Time.

### Một số File trong hệ thống Linux
DHCP Client Configuration: `/etc/dhcp/dhclient.conf` hoặc cấu hình `NetworkManager/systemd-networkd`.

DHCP Client Lease File: `/var/lib/dhcp/dhclient.leases`

ISC-DHCP-Server Config: `/etc/dhcp/dhcpd.conf`

ISC-DHCP-Server Lease Database: `/var/lib/dhcp/dhcpd.leases`

Dnsmasq (DHCP/DNS Lightweight): `/etc/dnsmasq.conf`

Log files: `/var/log/syslog` hoặc `journalctl -u isc-dhcp-server`

### Cấu hình như thế nào?
File `/etc/dhcp/dhcpd.conf` (ISC-DHCP-Server):
```
default-lease-time 600;
max-lease-time 7200;
authoritative;

subnet 192.168.0.0 netmask 255.255.255.192 {
  range 192.168.0.10 192.168.0.60;
  option routers 192.168.0.1;
  option domain-name-servers 1.1.1.1, 8.8.8.8;
  option domain-name "internal.lan";
}

# Gán IP tĩnh theo MAC Address
host server-db {
  hardware ethernet 00:11:22:33:44:55;
  fixed-address 192.168.0.5;
}
```
### Cơ chế hoạt động(DORA)
```
[Client: 0.0.0.0]                               [DHCP Server]
       │                                              │
       ├─── 1. DISCOVER (Broadcast 255.255.255.255) ──►│
       │                                              │
       │◄── 2. OFFER (Unicast/Broadcast) ─────────────┤
       │                                              │
       ├─── 3. REQUEST (Broadcast 255.255.255.255) ──►│
       │                                              │
       │◄── 4. ACK (Unicast/Broadcast) ───────────────┘
```
Discover: Client mới vào mạng phát gói Broadcast tìm DHCP Server.

Offer: Server nhận được gói Discover, đề nghị cấp một dải IP còn trống (YIADDR).

Request: Client phát Broadcast xác nhận đồng ý nhận IP từ Server đó (Broadcast để các DHCP Server khác biết mà thu hồi đề nghị).

ACK: Server ghi thông tin vào Lease Database và gửi xác nhận cấp quyền sử dụng IP trong khoảng thời gian Lease Time.

### Ưu / Nhược điểm
Ưu điểm: Tự động hóa hoàn toàn việc cấp phát IP, loại bỏ rủi ro trùng IP thủ công.

Nhược điểm: Phụ thuộc vào Server trung tâm; nguy cơ bị tấn công Rogue DHCP Server (DHCP giả mạo) hoặc DHCP Starvation Attack (làm kiệt huệ kho IP).

## 4. SSH (Secure Shell)
### Khái niệm
SSH là giao thức mạng cho phép thiết lập kênh giao tiếp bảo mật, được mã hóa giữa Client và Server qua mạng không tin cậy.

### Dùng để làm gì?
Truy cập dòng lệnh quản trị hệ thống từ xa (Remote CLI Execution).

Truyền tải file an toàn (SFTP / SCP).

Tạo đường hầm mã hóa (SSH Tunneling / Port Forwarding / SOCKS5 Proxy).

### Cấu trúc thành phần
Bộ giao thức SSH (Port 22 TCP) gồm 3 tầng con chính:
```
+-------------------------------------------------------+
| SSH Connection Protocol (Channels, Shell, Forwarding)  |
+-------------------------------------------------------+
| SSH User Authentication Protocol (Pubkey, Password)   |
+-------------------------------------------------------+
| SSH Transport Layer Protocol (Encryption, Integrity)  |
+-------------------------------------------------------+
```
- Transport Layer: Đảm nhiệm trao đổi khóa (Key Exchange), mã hóa đối xứng (Symmetric Encryption) và kiểm tra toàn vẹn dữ liệu (MAC - Message Authentication Code).
- User Authentication Layer: Xác thực danh tính người dùng (Public Key, Password, Keyboard-Interactive).
- Connection Layer: Quản lý đa luồng (Multiplexing) các kênh logic (Interactive Shell, Exec, SFTP, Direct-TCP/IP forwarding).

### Các file hệ thống trong Linux
SSH Daemon Config: `/etc/ssh/sshd_config`

SSH Client Config: `/etc/ssh/ssh_config` (Global) và `~/.ssh/config` (Per-user)

Server Host Keys: `/etc/ssh/ssh_host_rsa_key`, `/etc/ssh/ssh_host_ed25519_key`

User Authorized Keys: `~/.ssh/authorized_keys` (Chứa Public Key của Client được cấp quyền truy cập)

User Known Hosts: `~/.ssh/known_hosts` (Lưu thông tin Fingerprint Host Key của các Server đã từng nối đến)

Log files: `/var/log/auth.log` (Debian/Ubuntu) hoặc `/var/log/secure` (RHEL/CentOS)

### Cấu hình như thế nào?
File `/etc/ssh/sshd_config`:
```
Port 2222                          # Đổi cổng mặc định
PermitRootLogin no                 # Cấm đăng nhập trực tiếp bằng tài khoản root
PasswordAuthentication no           # Tắt đăng nhập bằng mật khẩu
PubkeyAuthentication yes           # Chỉ cho phép đăng nhập bằng SSH Key
AuthorizedKeysFile .ssh/authorized_keys
MaxAuthTries 3                     # Giới hạn số lần thử mật khẩu
ClientAliveInterval 300            # Chống drop connection timeout
```
### Cơ chế hoạt động:
TCP Handshake: Kết nối Tầng 4 thành công qua Port 22.

Protocol Version Exchange: Hai bên gửi chuỗi thông tin phiên bản (ví dụ `SSH-2.0-OpenSSH_9.6`).

Key Exchange (KEX): Dùng thuật toán ECDH hoặc DH để hai bên tự tính toán ra một Session Key dùng chung mà không cần gửi chìa khóa trực tiếp qua đường dây truyền tin.

Encryption Initialization: Bật mã hóa đối xứng (AES-GCM/ChaCha20) cho toàn bộ luồng dữ liệu đằng sau.

User Authentication: Client gửi SSH Key / Password để Server đối chiếu xác thực.

Channel Open: Mở kênh làm việc (Shell/SFTP).

### Ưu / Nhược điểm
Ưu điểm: Tính bảo mật cao, mã hóa toàn bộ dữ liệu, tích hợp công cụ Tunneling/Proxy mạnh mẽ.

Nhược điểm: Dễ bị tấn công Brute-Force vào Port 22 nếu dùng Password; cần quản lý khóa Public Key cẩn thận trong các hạ tầng lớn.

# Tầng Presentation
Tầng 6 (Presentation Layer) trong mô hình OSI chịu trách nhiệm chuyển đổi định dạng dữ liệu (Data Formatting/Serialization), mã hóa/giải mã an toàn (Encryption/Decryption), và nén/giải nén dữ liệu (Compression/Decompression) trước khi chuyển dữ liệu giữa Layer 7 (Ứng dụng) và Layer 4 (Transport).

## 1. TLS/SSL (Transport Layer Security)
### Khái niệm
TLS (tiền thân là SSL) là giao thức bảo mật Tầng Trình diễn. Mặc dù được chèn trực tiếp ngay trên Layer 4 (TCP), nhưng về mặt chức năng OSI, TLS chịu trách nhiệm mã hóa và giải mã toàn bộ luồng dữ liệu của các giao thức Layer 7 trước khi đóng gói xuống socket.

### Dùng để làm gì?
Mã hóa lưu lượng dữ liệu truyền qua mạng, biến Plaintext thành Ciphertext (bảo vệ HTTP $\rightarrow$ HTTPS, SMTP $\rightarrow$ SMTPS, WebSocket $\rightarrow$ WSS).

Đảm bảo tính toàn vẹn dữ liệu (chống sửa đổi gói tin giữa đường) và xác thực danh tính máy chủ thông qua chứng chỉ số (Digital Certificate X.509).

### Cấu trúc thành phần
TLS gồm 2 lớp giao thức con chính:
- TLS Record Protocol: Đóng gói, nén (nếu có), tính mã MAC và mã hóa dữ liệu.
- TLS Handshake Protocol: Thỏa thuận phiên bản, chọn Cipher Suite, xác thực Certificate và tạo Session Key.

Cấu trúc TLS Record Header (5 bytes):
```
+-------------------+-------------------+-------------------+
| Content Type (1B) | Version (2 Bytes) | Length (2 Bytes)  |
+-------------------+-------------------+-------------------+
|               Encrypted Payload (Data)                    |
+-----------------------------------------------------------+
```
Content Type (1 Byte): 20 (ChangeCipherSpec), 21 (Alert), 22 (Handshake), 23 (Application Data).

Version (2 Bytes): 0x0303 (TLS 1.2), 0x0304 (TLS 1.3).

Length (2 Bytes): Độ dài của khối dữ liệu mã hóa đi kèm.

### Các file hệ thống trong Linux
CA Trust Store (Kho chứa chứng chỉ gốc tin cậy):
- Debian/Ubuntu: `/etc/ssl/certs/`, `/usr/local/share/ca-certificates/`
- RHEL/CentOS: `/etc/pki/tls/certs/`, `/etc/pki/ca-trust/extracted/`

File cấu hình OpenSSL: `/etc/ssl/openssl.cnf`

Chứng chỉ Let's Encrypt (Certbot): `/etc/letsencrypt/live/<domain>/` (`fullchain.pem`, `privkey.pem`)

### Cấu hình như thế nào?
Ta có thể tự tạo chứng chỉ tự ký (Self-Signed Certificate) bằng OpenSSL CLI trên Linux:
```
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/server.key \
  -out /etc/ssl/certs/server.crt \
  -subj "/C=VN/ST=Hanoi/O=DevOps/CN=api.internal.lan"
```
### Cơ chế hoạt động
Hoạt động theo mô hình Cliet-Server
```
Client                                                   Server
  │                                                        │
  ├─── 1. ClientHello (CipherSuites + Key Share) ─────────►│
  │                                                        │
  │◄── 2. ServerHello (Selected Suite + Key Share) ────────┤
  │    3. EncryptedExtensions                              │
  │    4. Certificate (X.509)                              │
  │    5. CertificateVerify                                │
  │◄── 6. Finished ────────────────────────────────────────┤
  │                                                        │
  ├─── 7. Finished ────────────────────────────────────────►│
  │                                                        │
  [────── Sẵn sàng truyền Application Data (Encrypted) ────]
```
- ClientHello: Client gửi danh sách thuật toán hỗ trợ kèm tham số công khai để trao đổi khóa (Key Share).
- ServerHello: Server chọn thuật toán, tính toán ra Master Secret Key, gửi kèm Chứng chỉ số (Certificate).
- Encrypted Response: Ngay từ bước này, mọi gói tin của Server gửi về đã được mã hóa bằng chìa khóa tạm thời.
- Client Finish: Client xác thực Certificate qua CA, tự tính ra Master Secret Key tương tự, xác nhận hoàn tất và bắt đầu truyền dữ liệu an toàn.

### Ưu / Nhược điểm
Ưu điểm: Độ an toàn tuyệt đối, ngăn chặn nghe lén (Sniffing) và tấn công Man-in-the-Middle (MitM).

Nhược điểm: Tốn tài nguyên CPU để mã hóa/giải mã; tăng độ trễ kết nối ban đầu (1-RTT hoặc 2-RTT).

## 2. Protocol Buffers/ Protobuf (Data Serialization)
### Khái niệm
Protobuf là cơ chế mã hóa và tuần tự hóa dữ liệu (Data Serialization) định dạng nhị phân do Google phát triển. Nó hoạt động như một "phiên dịch viên Layer 6", chuyển đổi các Struct/Object trong mã nguồn thành chuỗi byte cực nhỏ để truyền qua mạng.

### Dùng để làm gì?
Chuẩn hóa và đóng gói dữ liệu trong hệ thống gRPC, Microservices và giao tiếp IPC giữa các ứng dụng requiring hiệu năng cao.

Thay thế cho định dạng JSON/XML ở những hệ thống cần tối ưu băng thông và tốc độ xử lý.

### Cấu trúc thành phần
Dữ liệu Protobuf không lưu tên biến ở dạng Text như JSON. Nó sử dụng cơ chế Tag-Length-Value (TLV) dựa trên con số định danh (Field Number) được định nghĩa trong file Schema `.proto`.

### Các file hệ thống trong Linux
Compiler CLI: `/usr/bin/protoc` (Chương trình biên dịch file .proto sang code C++, Python, Go, Java...).

Library Header Files: `/usr/include/google/protobuf/`

File Schema định nghĩa: Có phần mở rộng `.proto` do lập trình viên viết.
### Cấu hình như thế nào
Tạo file Schema `user.proto`:
```
syntax = "proto3";

package user;

message UserRequest {
  int32 user_id = 1;     // Field Number = 1
  string email = 2;       // Field Number = 2
}
```
Biên dịch ra code Python trên Linux
```
protoc --python_out=. user.proto
```
### Cơ chế hoạt động
```
[App Code (Python Object)] ──(Serialize via Protobuf)──> [Binary Stream (0x08 0x01 0x12...)]
                                                                    │ (Truyền qua Layer 4 TCP)
[App Code (Go Struct)]     <──(Deserialize via Protobuf)────────────┘
```
Serialization (Gói dữ liệu): Nhận Object từ ứng dụng, tra cứu file `.proto` để map các trường dữ liệu thành các cờ Tag nhị phân ngắn gọn, nén số nguyên và mã hóa thành chuỗi bytes.

Deserialization (Mở gói dữ liệu): Máy nhận đọc chuỗi bytes, dùng file `.proto` tương ứng để dựng ngược lại thành Struct/Object trong bộ nhớ RAM của ngôn ngữ đích.

### Ưu / Nhược điểm
Ưu điểm: Kích thước gói tin nhỏ hơn 3-10 lần so với JSON, tốc độ nén/giải nén nhanh hơn 2-5 lần, hỗ trợ kiểm tra kiểu dữ liệu nghiêm ngặt (Strict Schema Validation).

Nhược điểm: Chuỗi nhị phân không thể đọc được bằng mắt thường (Human-unreadable); bắt buộc hai bên phải sở hữu chung file `.proto` mới có thể đọc được dữ liệu.

# Tầng Session
Tầng 5 (Session Layer / Tầng Phiên) trong mô hình OSI chịu trách nhiệm thiết lập (Establishment), duy trì (Maintenance), đồng bộ hóa (Synchronization/Checkpointing) và giải phóng (Termination) các phiên hội thoại giữa 2 ứng dụng ở hai đầu cuối.
## 1. gRPC/RPC
### Khái niệm
RPC là mô hình điều khiển phiên làm việc cho phép một chương trình gọi thực thi một hàm/thủ tục trên một máy chủ từ xa như thể đó là một hàm cục bộ. gRPC là framework RPC hiện đại do Google phát triển, hoạt động như một lớp quản lý phiên kết nối và luồng dữ liệu nâng cao trên nền HTTP/2.

### Dùng để làm gì?
Quản lý ngữ cảnh thực thi (Execution Context), truyền nhận tham số và trạng thái kết nối giữa các Microservices.

Hỗ trợ các kiểu phiên giao tiếp linh hoạt: Unicast RPC, Client Streaming, Server Streaming, và Bi-directional Streaming (Truyền hai chiều thời gian thực).

### Cấu trúc thành phần
Một phiên gRPC gồm các thành phần logic:
```
[ Client Application ] ──> [ Stub (Client Session Manager) ]
                                      │ (Channel / Session Abstraction)
[ Server Application ] <── [ Service Skeleton / Handler ]
```
Channel: Đối tượng trừu tượng đại diện cho một phiên kết nối lâu dài (Persistent Connection) tới Server. Channel quản lý việc tự khôi phục kết nối (Reconnection), cân bằng tải phía Client (Client-side LB) và giữ trạng thái kết nối.

Stub: Mã đại lý ở phía Client, chịu trách nhiệm đóng gói tham số hàm và khởi tạo phiên gọi hàm từ xa.

HTTP/2 Streams: Mỗi phiên gọi thủ tục được ánh xạ thành 1 Stream độc lập trên cùng 1 kết nối TCP vật lý.

### Các file hệ thống trong Linux
Compiler Utility: `/usr/bin/protoc` (Biên dịch giao diện gRPC từ file `.proto`).

Cấu hình Service Backend: Thường được quản lý qua systemd file `/etc/systemd/system/grpc-app.service`.

File định nghĩa giao diện (IDL): Các file `.proto` chứa thông tin các hàm (Service Services) và kiểu dữ liệu.

### Cấu hình như thế nào
Định nghĩa Service Session trong file `service.proto`:
```
syntax = "proto3";

package analytics;

service TelemetryService {
  // Session truyền luồng dữ liệu 2 chiều thời gian thực
  rpc StreamMetrics (stream MetricRequest) returns (stream MetricResponse);
}

message MetricRequest { string host_id = 1; double cpu_usage = 2; }
message MetricResponse { string status = 1; }
```
Khởi tạo gRPC Channel (Phiên kết nối) bằng Python trên Linux:
```
import grpc
import service_pb2_grpc

# Thiết lập Channel (Duy trì Session Tầng 5)
channel = grpc.insecure_channel('192.168.0.50:50051')
stub = service_pb2_grpc.TelemetryServiceStub(channel)
```
### Cơ chế hoạt động
Khởi tạo Session (Channel Creation): Client khởi tạo Channel kết nối tới Server. Channel kiểm tra trạng thái và duy trì kết nối ở background.

Khởi tạo phiên hàm (RPC Call): Client gọi hàm qua Stub $\rightarrow$ Stub tạo một Stream ID mới trên kết nối HTTP/2.

Trao đổi dữ liệu (Context & Payload): Gửi metadata (Timeout, Auth Token) kèm dữ liệu Protobuf đã được nén.

Đồng bộ & Kết thúc (Termination): Server xử lý xong, trả về Status Code (ví dụ: OK, CANCELLED, UNAVAILABLE) và đóng Stream ID đó lại, nhưng vẫn giữ nguyên Channel cho các phiên sau.
### Ưu / Nhược điểm
Ưu điểm: Quản lý phiên giao tiếp cực kỳ hiệu quả, hỗ trợ Streaming 2 chiều độ trễ thấp, tự động tái tạo kết nối khi đứt mạng.

Nhược điểm: Đòi hỏi định nghĩa Schema chặt chẽ; khó kiểm tra/debug trực tiếp bằng các công cụ Plaintext thô.
