# OpenStack Glance — Image Service

## 1. Khái niệm

**Glance** là dịch vụ quản lý **disk image** (ảnh đĩa máy ảo) trong OpenStack. Nó đóng vai trò là kho lưu trữ trung tâm và cung cấp các "bản thiết kế" hệ điều hành (OS image / snapshot) để các dịch vụ khác — chủ yếu là **Nova** và **Cinder** — lấy ra khởi tạo máy ảo hoặc tạo bootable volume.

> **Hình dung thực tế:** Glance giống như một **thư viện sách** — nó không tự chạy máy ảo thay cho Nova, nhưng lưu trữ, đánh chỉ mục catalog và cấp đúng cuốn sách (image) khi có yêu cầu.

**Vai trò chính:**

* Tiếp nhận và xử lý các yêu cầu HTTP REST API liên quan đến disk image và metadata.

* Lưu trữ dữ liệu nhị phân của image trên nhiều loại backend khác nhau (Local Filesystem, Ceph RBD, Swift, S3, HTTP...).

* Quản lý metadata của image (tên, định dạng đĩa, định dạng đóng gói, kích thước, trạng thái, checksum/hash, quyền hiển thị...).

* Lưu trữ và quản lý **snapshot** của máy ảo đang chạy để sao lưu hoặc nhân bản hàng loạt.

## 2. Lợi ích cốt lõi (Advantages)

| Lợi ích | Giải thích | 
| ----- | ----- | 
| **Tính nhất quán** | Mọi máy ảo khởi tạo từ cùng một image đều có cấu hình hệ điều hành và phần mềm ban đầu giống hệt nhau. | 
| **Tốc độ triển khai** | Khi kết hợp với backend hỗ trợ Copy-on-Write (như **Ceph RBD**), việc nhân bản và khởi tạo VM diễn ra gần như tức thì mà không cần copy toàn bộ dung lượng file ảnh. | 
| **Linh hoạt Storage Backend** | Hỗ trợ lưu trữ trên Local File System, Ceph, Swift, S3... dễ dàng mở rộng hoặc thay đổi theo quy mô hạ tầng. | 
| **Phân quyền & chia sẻ** | Kiểm soát chặt chẽ phạm vi truy cập image thông qua các mức `visibility` (`public`, `private`, `shared`, `community`). | 
| **Độc lập, dễ mở rộng** | Là một dịch vụ tách biệt hoàn toàn với Nova, có thể scale riêng tiến trình `glance-api` khi lưu lượng tải/cấp phát image tăng cao. | 

## 3. Kiến trúc & Thành phần

Glance hoạt động theo mô hình **client-server**, cung cấp giao diện **REST API** (mặc định lắng nghe ở cổng **`9292`**) để người dùng và các dịch vụ OpenStack khác giao tiếp.

### 3.1. Các thành phần chính

| Thành phần | Vai trò | Ghi chú | 
| ----- | ----- | ----- | 
| **Client** | Bất kỳ công cụ/dịch vụ nào gọi tới Glance API (`openstack` CLI, Nova, Cinder, Horizon...). | Giao tiếp qua HTTP REST. | 
| **REST API (`glance-api`)** | Tiến trình chính tiếp nhận request, xác thực token qua **Keystone** và điều phối thao tác lưu trữ/truy xuất image. | Thành phần trung tâm, luôn chạy nền. | 
| **Domain Controller** | Tầng middleware xử lý logic nghiệp vụ: phân quyền (`authorization`), kiểm tra `policy`, hạn mức (`quota`) và gửi thông báo (`notification`). | Nằm bên trong `glance-api`. | 
| **DAL** (*Database Abstraction Layer*) | Lớp trừu tượng hóa giao tiếp giữa Glance và hệ quản trị cơ sở dữ liệu. | Sử dụng SQLAlchemy. | 
| **Database (`glance`)** | Lưu trữ **metadata** của image: `id`, `name`, `disk_format`, `container_format`, `status`, `visibility`, `checksum`, `size`, `location`... | MariaDB / PostgreSQL. | 
| **Glance Store (`glance_store`)** | Thư viện trừu tượng hóa giao tiếp giữa Glance và các storage backend. | Cung cấp giao diện đọc/ghi thống nhất. | 
| **Storage Backend** | Nơi lưu **file nhị phân thực tế** của image (từ vài chục MB tới hàng chục GB). | Local Filesystem (`/var/lib/glance/images/`), Ceph, Swift, S3, HTTP. | 

> **Lưu ý kiến trúc:** Thành phần cũ `glance-registry` đã bị **deprecated** và loại bỏ hoàn toàn từ bản OpenStack Queens trở đi. Trên Ubuntu 24.04 hiện tại, bạn chỉ triển khai và vận hành dịch vụ **`glance-api`** (kèm tệp cấu hình chính `/etc/glance/glance-api.conf`).

### 3.2. Tại sao Glance tách biệt Database và Storage Backend?

Glance tách metadata (lưu ở SQL Database) khỏi dữ liệu ảnh thực tế (lưu ở Storage Backend) vì 3 lý do kỹ thuật:

1. **Hiệu năng truy vấn & ổn định DB:** Cơ sở dữ liệu quan hệ (MariaDB) được tối ưu cho các bản ghi nhỏ và tìm kiếm có chỉ mục; lưu hàng trăm GB/TB dữ liệu nhị phân trực tiếp vào DB sẽ gây phình dung lượng, nghẽn I/O và dễ hỏng dữ liệu.

2. **Tách biệt hạ tầng lưu trữ:** Metadata nằm gọn ở MariaDB trên `controller`, còn dữ liệu ảnh có thể đặt ở thư mục cục bộ (trong lab All-in-One) hoặc đẩy sang Ceph/Swift/S3 (trong production) mà không làm thay đổi cấu trúc quản lý.

3. **Liệt kê & lọc cực nhanh:** Các thao tác như `openstack image list` hoặc `openstack image show` chỉ cần đọc metadata từ MariaDB, hoàn toàn không phải quét vào kho lưu trữ nhị phân.

### 3.3. Luồng hoạt động thực tế — Nova tạo VM từ Image

```
[1. Nova (nova-api / nova-compute)] ──(Gửi request + Token)──> [2. Glance API (:9292)]
                                                                       │
                                            ┌──────────────────────────┼──────────────────────────┐
                                            ▼                          ▼                          ▼
                                    [3. Keystone]              [4. Glance DB]          [5. Glance Store]
                                 (Xác thực Token &          (Truy vấn metadata &      (Đọc file nhị phân từ
                                  kiểm tra quyền)            địa chỉ location)          Storage Backend)
                                                                       │                          │
                                                                       └────────────┬─────────────┘
                                                                                    ▼
                                                                  [6. Trả dữ liệu Image về Compute Node]
                                                                    (Tạo ổ đĩa gốc & boot máy ảo)

```

**Các bước chi tiết:**

1. Khi nhận lệnh tạo VM, **Nova** (`nova-api` kiểm tra thông tin ban đầu và `nova-compute` trên node tính toán thực hiện tải ảnh) gửi request tới **`glance-api`** kèm theo token xác thực.

2. **`glance-api`** chuyển token sang **Keystone** để xác thực danh tính và kiểm tra quyền truy cập image qua `Domain Controller`.

3. Glance truy vấn **Database (`glance`)** thông qua `DAL` để kiểm tra trạng thái image (`active`) và lấy thông tin `location` (nơi chứa file ảnh).

4. Glance thông qua **`glance_store`** đọc luồng dữ liệu nhị phân từ **Storage Backend** (ví dụ `/var/lib/glance/images/<image_uuid>`).

5. Dữ liệu image được truyền về `nova-compute` để tạo disk (thường cache lại trên compute node cho các VM sau) và khởi động máy ảo trên hypervisor (`KVM/libvirt`).

## 4. Định dạng Image, Vòng đời & Phân quyền hiển thị

### 4.1. Disk Format (`--disk-format`)

Định dạng của tệp ảnh đĩa — quyết định cấu trúc lưu trữ dữ liệu bên trong file:

| Format | Mô tả | Khi nào dùng | 
| ----- | ----- | ----- | 
| `qcow2` | QEMU Copy-on-Write v2, hỗ trợ cấp phát động (thin provisioning), nén và snapshot. | **Phổ biến nhất trên KVM/QEMU** và trong môi trường lab. | 
| `raw` | Định dạng đĩa thô, không nén, không bọc metadata định dạng. | Hiệu năng I/O cao nhất, đặc biệt tối ưu khi dùng với **Ceph RBD**. | 
| `vhd` / `vhdx` | Định dạng đĩa ảo của Microsoft Hyper-V. | Khi chuyển đổi (migrate) máy ảo từ môi trường Hyper-V. | 
| `vmdk` | Định dạng đĩa ảo của VMware. | Khi chuyển đổi máy ảo từ môi trường VMware vSphere/ESXi. | 
| `iso` | Ảnh đĩa quang chuẩn ISO 9660. | Dùng khi cần boot từ đĩa cài đặt OS thủ công. | 

### 4.2. Container Format (`--container-format`)

Mô tả cách **đóng gói** (wrapper) bên ngoài của tệp image — không làm thay đổi nội dung hệ điều hành bên trong:

| Format | Mô tả | 
| ----- | ----- | 
| `bare` | Không có lớp vỏ đóng gói bên ngoài — **dùng cho hầu hết mọi trường hợp**. | 
| `ovf` / `ova` | Định dạng đóng gói máy ảo mở (Open Virtualization Format / OVA tar archive). | 
| `aki` / `ari` / `ami` | Bộ định dạng kernel, ramdisk và machine image kiểu Amazon cũ. | 
| `docker` | Tệp lưu trữ tar của hệ thống tệp container. | 

> **Lưu ý thực tế:** `container_format` chủ yếu phục vụ mục đích ghi nhận metadata. Khi upload image (`qcow2`, `raw`, `iso`...), **mặc định luôn chọn `bare`**.

### 4.3. Vòng đời trạng thái Image (`Status Lifecycle`)

Từ lúc tạo metadata cho tới khi sẵn sàng sử dụng hoặc bị xóa, một image đi qua các trạng thái sau:

```
[Create request]
       │
       ▼
    QUEUED ──(Bắt đầu upload)──> SAVING ──(Upload hoàn tất)──> ACTIVE
       │                            │
       │                      (Lỗi upload)
       │                            │
       │                            ▼
       │                         KILLED
       │
    ACTIVE ──(Admin vô hiệu hóa)──> DEACTIVATED
       │
    ACTIVE ──(Lệnh xóa image)────> PENDING_DELETE ──> DELETED

```

| Trạng thái | Ý nghĩa | 
| ----- | ----- | 
| `queued` | Đã đăng ký metadata trong DB `glance`, chưa có dữ liệu nhị phân được tải lên. | 
| `saving` | Đang trong quá trình nhận và ghi dữ liệu nhị phân xuống storage backend. | 
| `active` | Upload thành công, tính toàn vẹn hợp lệ, sẵn sàng dùng để khởi tạo VM. | 
| `killed` | Quá trình upload bị lỗi hoặc dữ liệu hỏng, không thể sử dụng. | 
| `deactivated` | Bị quản trị viên tạm khóa (vẫn giữ dữ liệu nhưng không cho download hoặc boot VM mới). | 
| `pending_delete` | Đã nhận lệnh xóa và đang chờ tiến trình dọn dẹp (`glance-scrubber`) xóa file vật lý. | 
| `deleted` | Đã xóa hoàn toàn khỏi hệ thống. | 

### 4.4. Quyền hiển thị Image (`Visibility`)

| Mức độ | Phạm vi truy cập | 
| ----- | ----- | 
| `public` | Mọi project trong toàn bộ hệ thống OpenStack đều thấy và dùng được (mặc định chỉ `admin` mới tạo được). | 
| `private` | Chỉ project sở hữu image mới thấy và sử dụng được (mặc định khi user thường tạo image). | 
| `shared` | Image riêng tư nhưng được chủ sở hữu chia sẻ tường minh cho một hoặc nhiều project cụ thể (`member`). | 
| `community` | Hiển thị công khai cho mọi project trong cộng đồng người dùng nhưng không tự động xuất hiện trong danh sách mặc định nếu không lọc theo `community`. |
